# Design: the proxy transaction driver

**Status:** proposed · **Pillar:** Signalling · **Epic:** `proxy-engine` · **Story:** PX-2 ·
**Spec:** [proxy-behavior](../specs/proxy-behavior.md)

## Why

[`proxy-behavior.md` §2](../specs/proxy-behavior.md) defines the engine as a pure state machine:
inputs go in, an ordered list of `Effect`s comes out. Something has to *perform* those effects —
put bytes on a socket, create and cancel transactions, set timers, ask the location service — and
that something is the driver. This design says exactly what it is built on and what it owes the
engine, so `PX-5` implements a core against a settled seam rather than inventing one as it goes.

The decision the epic design left open is the one this settles: **the crate boundary against
`sipx-transport`** — what is imported, what is extracted upstream, what is written here.

## The finding that decides it

The epic design assumed sipx's transport API was "UA-shaped: one transaction, one target",
and that a forking proxy would therefore have to be built directly on
`sipx_sip::transaction::TransactionLayer`, with its own socket loop.

Reading 0.2.1 rather than remembering it: **that assumption is wrong in the way that matters.**
`sipx_transport::Handle` already fans out.

| What a forking proxy needs | What 0.2.1 gives it |
|---|---|
| N concurrent client transactions from one request | `Handle::send(request, target) -> Responses`, called N times. Each call creates one client transaction; each returns its own event stream. The endpoint's `TransactionLayer` holds N client + M server transactions in one store already. |
| Control of the `Via` we push | `send` inserts a `Via` **only if absent** (`endpoint.rs:286`). A proxy pushes its own, with the RFC 5393 cookie, and `send` leaves it alone. |
| The branch we chose to *be* the transaction key | It is: the key derives from the top `Via` branch, so the branch id in the engine and the transaction identity in the kernel are the same string. |
| Respond upstream, provisionals then final | `Handle::respond(&TransactionKey, Response)`, repeatable. |
| The server transaction's key for an arriving request | `Incoming { key, request, source, transport }` — with `received` and `rport` already applied to the topmost `Via`. |
| Send with no transaction (2xx ACK, stateless mode) | `Handle::send_directly(request, target)`. |
| ACK for a non-2xx final | Generated by the kernel's client transaction (RFC 3261 §17.1.1.3). Not our job. |
| A connection pool, TLS/WS/WSS, RFC 3263 resolution, retransmission timing | `Pool`, `PoolConfig`, `Resolver`, `resolve`, `Target`, `TransportKind` — all public, all released, all interop-tested. |

**Decision: the driver is built on `sipx_transport::Handle`.** Not on a socket loop of our own.

The alternative — own the `TransactionLayer` and drive our own sockets — buys control over two
small gaps (below) at the cost of reimplementing the framing, the three handshakes, the NAT
`Via` rewriting, the pool and the retransmission driver. That is thousands of lines of released
kernel code, and rewriting it here is precisely what AGENTS.md rule 6 forbids: sipx-clstr never
shadow-implements kernel logic, "even when building it here would be faster today".

## Two real gaps, and why neither blocks M1

Reading the endpoint's dispatch (`endpoint.rs:928`) turns up two things a UA does not care about
and a proxy does.

**1. Unmatched *responses* are dropped.** `Dispatch::Unmatched` forwards only
`Message::Request` to the application; a response matching no client transaction is logged and
discarded. RFC 3261 §16.7 step 1 requires a stateful proxy that finds no response context to
forward the response **statelessly** instead. A UA has nothing useful to do with a stray
response, so the kernel's behaviour is right for its own consumers and wrong for ours.

**2. `Incoming` is delivered with `try_send`.** When the application is slower than the network,
requests are dropped silently. For a UA under load that is a missed call. For a proxy it is worse
and quieter: **a dropped 2xx ACK is a call that stays established forever**, because the ACK is
the only thing that would have concluded it, and nothing retransmits it after Timer H. Silent loss
with no counter is the part that makes this a defect rather than a policy — you cannot even see it
happening.

Both are small, both are defensible on the kernel's own terms, and both are filed upstream rather
than worked around here (see the [ledger](../upstream.md)).

Neither blocks M1. Gap 1 shows up on a spiral or a stray response — in a **one-node** milestone
with no cluster and no token path, the response context is always found. Gap 2 shows up under
sustained overload, which M1 does not claim to survive; `RT-3` is where that claim gets made. Both
must be closed before M2 asserts "killing any single node leaves new calls working", because both
failure modes are exactly what node loss produces.

## Shape

One task per proxied request, owning its response context. No locks on the signalling path,
because there is nothing to lock: the context is not shared.

```text
   bind(Config) ──► Handle  +  Receiver<Incoming>
                      │              │
                      │       accept loop: one task per Incoming
                      │              │
                      │              ▼
                      │      ┌──────────────────────┐
                      │      │  response context    │   the sans-IO engine
                      │      │  (proxy-behavior §2) │   — no clock, no socket
                      │      └──────────┬───────────┘
                      │         Effect  │  Input
                      │                 ▼
                      │      ┌──────────────────────┐
                      └──────┤  the driver          │
                             │  · Forward → send()  │
                             │  · Respond → respond()│
                             │  · CancelBranch      │
                             │  · SetTimer → sleep  │
                             │  · ResolveTargets    │
                             └──────────────────────┘
```

**The branch loop.** Each `Forward` effect calls `Handle::send`, yielding a `Responses` stream.
The task holds them in a `FuturesUnordered`, so a branch's response, a fired timer and an upstream
CANCEL all arrive at one `select!` and are turned into one `Input` at a time. The engine therefore
sees a total order of inputs, which is what makes the same sequence replayable in the harness
under virtual time with no sockets at all.

**Effect ordering is load-bearing and preserved.** The engine emits `Forward` before the
`SetTimer` that guards it; the driver performs effects in order and awaits each. A Timer C that
started before its INVITE went out would be measuring the wrong interval.

## The effects, one by one

| Effect | Performed as | Notes |
|---|---|---|
| `Forward { branch, request, target, next_hop }` | `Handle::send` to `next_hop`'s address | The engine has already pushed the `Via` (with branch), decremented `Max-Forwards` and applied `Route`. The driver adds nothing to the message — a driver that edits a message is a rule the harness cannot see. It does not *choose* anything either: `next_hop` is the engine's F7 answer, and the driver only resolves it to an address. `PX-13` added the field, because the driver had been deriving the hop from `target.uri` — which is the URI the copy is *addressed* to, not the one it must be *sent* to, and the two differ for every route set and every registered `Path`. |
| `Respond(response)` | `Handle::respond(server_key, …)` | The engine has already popped our `Via`. |
| `CancelBranch(branch)` | mint a CANCEL, `Handle::send` | RFC 3261 §9.1: same Request-URI, `Call-ID`, `To`, `From` and `CSeq` number, method `CANCEL`, and **the same top `Via` branch** as the INVITE. We chose that branch, so we know it. A CANCEL is a non-INVITE client transaction of its own; the kernel retransmits and times it. |
| `ResolveTargets(query)` | location service or `resolve` | **Off the response-context task.** The answer returns as a `TargetsResolved` input. `RT-1` decides whether the resolver stays the kernel's synchronous one or becomes the shared-cache variant filed as sipx `T-17`. |
| `SetTimer` / `ClearTimer` | a `tokio` sleep per (timer, branch) | Timer C is ours, not the kernel's: RFC 3261 §16.8 puts it on the proxy, above the transaction. In the harness the same effect becomes an entry in the scheduler's queue. |
| `Terminate` | drop the task | The kernel reaps its own transactions. `Handle::outstanding()` is how a test asserts nothing leaked. |

## The `ACK`, which has no response context at all

`PX-13` settled the one arrival this shape does not describe. An `ACK` for a 2xx is a request in its
own right (RFC 3261 §17.1.1.3) and nothing answers it, so there is no server transaction to hold and
no response to aggregate — a `ResponseContext` would have nothing to do, and every refusal it can
reach (§7's `480`, §4's `483`) is a status that must not be sent.

It is still a **decision**, so it is still sans-IO: `sipx_clstr_proxy::route_ack` is a pure function
from the arriving `ACK` and the `ProxyConfig` to either a forwardable copy plus its next hop, or an
explicit unroutable outcome carrying a reason. The driver performs the first with
`Handle::send_directly` — no client transaction, because nothing will retransmit or time out an
`ACK` — and records the second. It cannot answer either one: `Handle::respond` is not reachable from
that path.

The two other messages the method name covers never reach the driver, and the kernel is what
guarantees it: the `ACK` for a non-2xx going downstream is minted by the client transaction that
received the final response, and the one arriving from upstream is absorbed by the server transaction
that sent it (`transaction/server.rs`, `Completed → Confirmed`). Only an `ACK` that matched no server
transaction, or matched one in `Accepted`, is handed up — and both of those are ACKs for a 2xx.

## Failure handling, per branch

`Responses` delivers `TuEvent`. The mapping to engine inputs is total, and it is the whole of the
driver's judgement:

| `TuEvent` | Input |
|---|---|
| `Response(r)` | `BranchResponse(r, branch)` |
| `TransportError` | `BranchTransportError(branch)` — §16.9, which the engine treats as a `503` from that branch |
| `Timeout` | `BranchResponse(408, branch)` — the spec's `PB-R-10` |
| `Ack(_)` | not expected on a proxy's client transaction; counted and dropped |
| stream ends with no final | `BranchTransportError(branch)` — a branch that vanishes is a branch that failed, and leaving the context waiting on it forever is the failure mode this row exists to prevent |

## Backpressure

Three places, named because an unnamed one becomes an incident:

1. **Inbound.** The `Receiver<Incoming>` is single-consumer; the accept loop must not do work
   inline. It spawns and returns. If it ever blocks, gap 2 above starts dropping requests
   silently.
2. **Outbound.** `Handle::send` is `async` over an `mpsc` to the endpoint's loop; awaiting it *is*
   the backpressure. The driver must not `try_send` its way around that.
3. **Per branch.** Each `Responses` stream is an `mpsc` the context task must drain. A context
   that stops draining stalls that branch only — which is the right blast radius, and is why the
   context is per request rather than shared.

Admission control — deciding *not* to accept — is `RT-3`, not this. What this design owes `RT-3`
is a place to put it: the accept loop, before the spawn.

## What runs in the harness

Everything above the `Handle`. `CF-5` substitutes a driver that performs the same effects against
a simulated network and a virtual clock, and feeds back the same `Input`s. Nothing in the engine
distinguishes the two, which is the property that makes `PX-1`'s vectors executable rather than
aspirational — and the reason the driver adds nothing to a message on its way out.

## Alternatives considered

- **Own the `TransactionLayer`, drive our own sockets.** Rejected above: it trades two small,
  upstreamable gaps for a rewrite of released, interop-tested kernel code.
- **One task per branch, sharing the context behind a mutex.** Rejected: a lock on the signalling
  path, and a context whose input order depends on scheduling is a context the harness cannot
  replay deterministically. Determinism is the north star; this would forfeit it for nothing.
- **Extend `Handle` with a proxy mode upstream.** Rejected for the same reason the epic design
  rejected extending the driver: it couples two roadmaps and destabilizes a shipped API, when the
  two things actually missing are a widened `Unmatched` and a non-lossy channel.

## Open questions

- Whether `ResolveTargets` uses the kernel's synchronous `Resolver` in M1 and switches later, or
  waits for sipx `T-17`. `RT-1`'s call; M1's location lookups are local, so the M1 answer is
  "kernel resolver, and it does not matter yet".
- Where the CANCEL's `Target` comes from when a branch failed over to a second candidate. The
  engine must carry the target it actually used per branch, not the one it planned. Settled in
  `PX-6` with the `PB-C-*` vectors.
